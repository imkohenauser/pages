# commit-ja

## 概要
ステージ済みの変更内容に基づき、**日本語** でコミットメッセージを1つ提案する。
git の状態を読み取りますが、ファイルの変更は行いません。コミットも作成しません。

## 手順
次を並列で実行し、それ以上は調べない。

- `git status --short`
- `git diff --cached --stat`
- `git diff --cached`
- `git log -8 --format='%s'`

ステージ済みの変更がなければ、その旨を1行で伝え、終了する。未ステージの変更は使わない。

件名はステージ済み diff から決める。コードベースの検索、ファイル全体の読解、仕様の推論はしない。パスと hunk だけでは件名が作れないときだけ、関係ファイルを1つまで読む。

既存スタイルは直近の件名だけから合わせる。CONTRIBUTING や commitlint を探さない。

## 分類
Conventional Commits の適切な type を決定する。
複数の type にまたがる場合は、コミットの分割を提案。
最も正確な type を選択:

- `feat`
- `fix`
- `docs`
- `style`
- `refactor`
- `perf`
- `test`
- `chore`
- `build`
- `ci`
- `revert`

scope はパスから明らかなときだけ付ける。破壊的変更は type の直後に `!` を付け、必要ならフッターに `BREAKING CHANGE:` を書く。

## 件名
- type と scope は英語、件名と本文は日本語。
- 件名は、このコミットを適用すると何が変わるかを体言止めで書く。「〜しました」は使わない。
- 変更の意味が分かる語を入れる。ファイル名の羅列、「修正」「更新」だけでは不十分。
- 件名末尾に句点を付けない。目安 50 字、上限 72 字。
- チケット番号や URL は件名に入れない。

## 出力
- プロジェクトの既存スタイル・ルールが存在すれば参照し、それに従う。
- 変更の要約を1行目に、必要なら2行目以降に補足を書く。本文は理由や影響。方法は書かない。
- メタ解説・導入文・締め・思考プロセスは一切禁止。
- 分割する場合は、メッセージを `---` で区切る。
- 例:

  ```
  feat(auth): OAuth2ログインエンドポイントを追加

  リフレッシュトークン対応の安全な認証フローを実装。
  バリデーションミドルウェアとエラー応答を含む。
  ```
